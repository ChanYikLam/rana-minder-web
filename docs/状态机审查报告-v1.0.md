## 1. 执行摘要

### 整体评价

RanaMinder-Web 项目拥有**设计完善的状态机规格体系**：29 个状态机、306+ 条精确转换规则已完整定义在 `src/mock/state-machines/transitions.ts` 中，配套 `spec-306.test.ts` 守护测试全量通过，`stateLabels.ts` 显示词表覆盖完整。状态机的**规格侧**已达到可签署水平。

然而，**实现侧**存在显著的接线缺口与一致性问题：

- **29 个状态机中，10 个完全未通过 `assertTransition` 接线**（占 34.5%），仅在转换表中定义但从未在业务代码中使用
- **SM-REC-004（部门路径与结论）完全裸奔**——6 个函数直接赋值 `path.status`，零校验
- **SM-EXP-001（导出任务）使用了状态机中不存在的 `'processing'` 状态**
- **换届执行绕过 SM-MEM-001/002**，`active -> exited` 跳过 `exiting` 中间态
- **UI 层存在 6 处非法状态转换按钮**，对不该操作的 状态显示了操作入口
- **超过 200 处硬编码状态字符串**散布在 40+ 个页面中，无编译期校验

### 2.2 设计原则

项目遵循以下状态机设计原则（来源：ADR-002 + SRS 状态机转换明细 v1.0）：

1. **单一事实来源**：`transitions.ts` 是所有状态与转换的唯一权威，`index.ts` 从中推导状态集，不维护第二套词表
2. **后端校验**：状态转换合法性校验集中在后端（Mock 层），前端不复制转换表
3. **事件级精确校验**：`assertTransition` 不仅校验 `from -> to` 可达性，还校验 `event` 是否匹配
4. **终态不可恢复**：已批准/已驳回/已取消/已过期/已归档/已删除状态不可回退
5. **唯一责任归属**：每个状态机归属一个领域模块，跨模块只能通过命令请求转换

## 4. 各层实现审查

### 4.1 状态机定义层（Mock/Types）

#### 转换表 `transitions.ts`

**评价：优秀。** 转换表设计严谨：

- 每个状态机以 `from -> { event: to }` 结构精确表达事件级转换
- 支持多目标转换（`string | readonly string[]`），如 `SM-IDN-002` 的 `save_profile: ['incomplete', 'pending_email_verification', 'complete']`
- `assertTransition` 函数（`transitions.ts:621-638`）实现四层校验：状态机存在性 → 源状态存在性 → 事件允许性 → 目标合法性
- `fromState == null` 时返回 `{ ok: true }`（`transitions.ts:629`），支持新建实体的首次状态设置

**发现的问题：**

- **SM-REC-003 的 `'accepted'` 状态不在转换表中**：`ApplicationStatus` 类型（`recruitment.ts:65-78`）包含 `'accepted'`，但 `SM-REC-003` 转换表（`transitions.ts:194-223`）的状态集为 `{draft, submitted, revision_requested, revised, exited, adjustment_overdue, identity_anomaly, not_qualified}`，不包含 `'accepted'`。`db-recruitment.ts:1627` 执行 `app.status = 'accepted'` 时绕过了状态机
- **SM-REC-003 的 `'revised'` 是死状态**：转换表中 `revised` 有出边（`submit -> submitted`）但无入边——没有任何事件的 `toState` 是 `'revised'`。该状态在业务代码中也未使用
- **SM-JNT-005 的 `accepted_locked` 是吸收态**：`accepted_locked: {}`（`transitions.ts:402`）无任何出边，是终态但未在注释中标注

#### 元数据推导 `index.ts`

**评价：良好。** `deriveStates` 函数（`index.ts:52-63`）从转换表自动推导状态集，避免手动维护第二套枚举。`isValidTransition`（`index.ts:92-106`）正确实现了可达性判定（不依赖事件名）。

#### 类型定义 `types/machine/index.ts`

**评价：合格。** `StateMachineId` 联合类型与 `TRANSITIONS` 的键完全一致（`spec-306.test.ts:96-99` 验证）。`PageState` 五态枚举与业务状态机正交，设计合理。

#### 显示词表 `stateLabels.ts`

**评价：良好。** `stateLabels.test.ts:9-18` 验证了每个状态机的每个合法状态都有中文标签映射。覆盖完整。

但存在以下显示别名（非状态机状态但保留了映射）：
- `opening`（`stateLabels.ts:82`）— 不在任何状态机中，是历史展示字段
- `configuring`（`stateLabels.ts:72`）— 不在任何状态机中
- `pending_publish`（`stateLabels.ts:73`）— 不在任何状态机中

```typescript
if (existing) return ok(existing)
```

其他写操作通过"状态已变化则拒绝"实现**弱幂等**。`IFC-ERR-009`（幂等键冲突）错误码已定义但从未使用。

### 4.3 服务层与组合式函数层

#### 状态校验

服务层**不包含任何状态机校验逻辑**。`assertTransition`、`TRANSITIONS`、`isValidTransition` 在 `mock/` 目录之外零引用。这是正确的架构决策——前端不复制转换表，完全依赖后端校验。

#### ApiResult 处理

`useRequest.ts:38-60` 正确映射了 6 种 ApiResult kind：

| ApiResult kind | PageState | 覆盖情况 |
|---------------|-----------|----------|
| `completed`（有 items 且空） | `empty` | ✅ |
| `completed`（非空） | `normal` | ✅ |
| `accepted` | `loading` | ✅ |
| `external_uncertain` | `loading` | ✅ |
| `concurrency_conflict` | `error` | ✅ |
| `dependency_unavailable` | `error` | ✅ |
| `rejected` | `errorToPageState(code)` | ✅ |

**但**：大多数页面不使用 `useRequest`，而是内联处理 ApiResult，导致 `external_uncertain` 和 `dependency_unavailable` 在 `.vue` 文件中**完全未处理**（0 处），落入兜底 `else` 分支显示通用错误。

`external_uncertain`（IFC-ERR-013：操作结果不确定）的语义是"操作可能已成功，请勿重复提交"，但前端将其当作普通错误处理，用户可能误以为操作失败而重新提交。

#### `operationStatusStore` — 孤儿 Store

`operationStatusStore`（33 行）设计了写操作状态跟踪机制（`pendingOperations` Map + `lastOperationResult`），但在所有 `.vue` 文件中**零引用**。仅有单元测试覆盖。页面实际采用了更简单的方式（局部 `submitting` ref + toast 提示），该 store 形同虚设。

#### `accepted` 后无统一轮询

仅 `ExportPage.vue:30-99` 实现了异步任务轮询（每 2 秒轮询，终态停止，组件卸载清理）。其他 11 处 `accepted` 处理仅设置 loading 态或 toast，用户无法获知异步操作最终结果。

### 4.4 UI 页面组件层

#### 状态引用方式

UI 层**完全不引用状态机定义**。在 `pages/` 和 `components/` 目录中（排除测试），没有任何一处导入 `assertTransition`、`TRANSITIONS`、`STATE_MACHINES` 或 `STATE_MACHINE_METAS`。

所有状态判断通过**硬编码字符串字面量**完成，超过 200 处分散在 40+ 个页面中。`StateMachineId` 和 `StateMachineMeta` 类型从未在 pages 中被引用。

#### StateTag 组件

`StateTag.vue`（21 行）接收 `status: string` prop，通过 `resolveStatusLabel()` 查找映射。未找到时**回退为 neutral 变体 + 原始 status 字符串**。这是静默降级策略——状态机新增状态但忘记更新 `stateLabels.ts` 时，用户会看到英文原文。

#### 非法状态转换按钮

详见 [5.2 节](#52-p1--高接线缺口与词表漂移) 问题 A-F。

### 9.4 术语表

| 术语 | 含义 |
|------|------|
| SM | State Machine（状态机） |
| 接线 | 状态机在业务代码中通过 `assertTransition` 实际使用 |
| 裸奔 | 状态机已定义但业务代码未使用 `assertTransition`，直接赋值状态 |
| 词表漂移 | 状态机定义的状态集与业务代码使用的状态字符串不一致 |
| 死状态 | 转换表中有出边但无入边的状态（不可达） |
| 吸收态 | 转换表中无出边的状态（终态） |
| 显示别名 | 不在状态机中但保留显示映射的历史状态字符串 |
