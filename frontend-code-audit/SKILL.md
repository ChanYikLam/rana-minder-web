# 前端代码审计

## 审计边界

将用户指定或设计文档定义的独立可验收前端切片视为一个审计阶段，例如一个页面、一个用户
流程、一组组件或一次跨端改动。不要把单条命令、单个文件或一次工具调用视为阶段。

默认只读审计：不修改代码、不格式化文件、不暂存、不提交、不推送。只有用户明确要求修复
时，才在审计结论后另开实现阶段；修复完成后必须重新审计受影响范围。

区分以下结论：

- **已验证**：有当前命令、构建、测试、运行截图或可复核代码证据支持。
- **设计覆盖**：规范或测试用例已描述，但本次没有执行验证。
- **未配置**：仓库没有对应脚本、测试或环境，不能写成通过。
- **推断风险**：依据代码路径或配置推断出的风险，标明缺少的运行证据。

## 设计一致性门禁

1. 阶段开始前，按“产品/交互设计 -> `docs/` 接口与权限约定 -> 根目录 `SKILL.md` 或
   `AGENTS.md` -> 前端配置与路由 -> 代码和测试”的顺序检查范围。
2. 核对页面入口、路由、参与者与权限、状态流转、请求与响应契约、表单校验、Loading/
   Empty/Error 状态、提交幂等、返回与刷新行为、平台能力和埋点/日志约束。
3. 后端接口或数据库设计不能替代前端交互和状态设计。发现数据契约无法支撑页面状态、
   权限、错误提示或重试行为时，记录为设计缺口，不用猜测规则掩盖问题。
4. 新增或改变页面、组件、路由、Store、接口调用或平台权限时，先确认对应设计、接口
   约定和配置已存在且未过期；缺失、冲突或无法唯一确定时，暂停高风险结论并向用户提出
   一个最重要的确认问题，附上推荐方案、备选方案和影响范围。
5. 既有设计足以确定实现时按设计审计；不要把“代码能编译”当作需求、权限、交互或数据
   流程正确的证据。

## 准备

1. 完整读取仓库根目录及目标目录作用域内的 `AGENTS.md`、`SKILL.md` 和贡献约定。
2. 检查 `package.json`、锁文件、构建工具、框架配置、入口文件、路由/页面配置、请求
   封装、Store、一个最接近的既有实现，以及本阶段相关设计文档。
3. 记录真实 `cwd`、当前分支、`git status --short --branch` 和阶段开始前的工作区差异。
   保留用户已有改动；不要把无关改动归因于本阶段，也不要覆盖或撤销它们。
4. 确认审计目标平台，例如 H5、微信小程序或其他 Taro 端；记录本次实际检查和构建的
   平台。未运行的平台只能写“未验证”。
5. 建立受影响清单：页面、页面配置、组件、Store、composable/util、请求与 Mock、样式、
   静态资源、路由、权限配置、测试和构建脚本。没有进入清单的文件不因局部搜索而直接判定
   全局安全。

## 审计架构与实现

### 1. 目录与依赖边界

- 页面入口、页面级组件、全局组件、基础组件、Store、工具和资源放在仓库约定目录。
- 页面级组件只服务所属页面；跨页面复用达到实际需要时再提升到全局目录，不为单次使用
  预先抽象。
- `base/` 保持展示原子职责，`common/` 承载明确的可复用业务组合；避免用目录名掩盖
  组件包含请求、权限或多套业务流程的问题。
- 检查跨子包引用、循环依赖、深层相对路径、别名失效和页面直接依赖另一个页面内部文件。
- 保持单向数据流：父组件通过 Props 下传，子组件通过 emit/回调上报；禁止子组件静默
  修改 Props 或绕过边界直接改动其他模块的状态。

### 2. Vue/Taro 运行时正确性

- 按项目基线使用 `<script setup>`、明确的组件名、Props 类型与默认值/必填约束、显式
  emits；TypeScript 项目不得新增 `any` 绕过类型边界。
- Taro 项目使用平台组件和正确事件，例如按仓库约定使用 `<view>`、`<text>`、`<image>`
  与 `@tap`；检查是否误用只适用于 Web 的标签、事件或浏览器 API。
- `v-for` 提供稳定且业务唯一的 `:key`；检查条件渲染、表单状态、异步数据到达前后的
  空值访问，以及组件卸载后的异步回写。
- 区分 Vue 生命周期与 Taro 页面生命周期；页面重新显示时需要刷新的逻辑应放在正确的
  页面钩子中，而不是只在首次挂载时执行。
- 页面跳转使用集中定义的路由常量或安全导航辅助函数；校验参数编码、目标白名单、返回
  栈、重复点击和 TabBar 同步，不直接信任 API 返回的完整跳转地址。
- 多步骤表单、弹窗或筛选页面检查状态是否在切换、返回、刷新和重新进入后保持正确；需要
  保留表单状态时核对 `v-show`、Store 或其他方案是否符合设计。

### 3. 状态、接口与异步流程

- 区分页面临时状态、组件状态和跨页面业务状态；Pinia Store 只保存真正共享的状态，避免
  把整个页面响应式对象或服务端缓存无边界地持久化。
- 每个异步请求明确处理 Loading、Success、Empty 和 Error；失败后可重试，且不会残留旧
  列表、重复提示或错误的提交按钮状态。
- 检查搜索防抖、分页、刷新、重复提交、请求取消和竞态响应；旧请求不能覆盖新筛选条件
  的结果。
- 核对请求参数、响应结构、业务错误码、鉴权失效、超时、网络错误和错误提示映射；UI 不
  直接展示后端原始堆栈、SQL、内部路径或敏感消息。
- 统一使用项目请求封装，检查 Token 注入、超时、重试、刷新、域名和错误处理是否被页面
  绕过；Mock 必须与真实契约一致，并且不能被误打进生产路径。
- 检查定时器、事件监听、订阅、IntersectionObserver、未完成请求和临时缓存是否在卸载或
  失效时清理。

### 4. 安全、隐私与供应链

- 搜索硬编码 API Key、Token、密码、私钥、内部域名、测试账号和完整个人信息；构建时注入
  的变量也不得被误认为秘密，前端包内任何内容都应按用户可见处理。
- 检查 URL、Query、Deep Link、扫码参数、富文本、图片地址和文件名等外部输入的类型、
  长度、编码、白名单和注入风险；禁止未清洗内容进入 HTML 或富文本渲染。
- 检查 Token、用户资料、手机号、位置和认证材料的本地存储、Pinia 持久化、日志、埋点和
  错误上报；只保存设计允许的数据并设置必要的生命周期。
- 检查远程 API、图片、下载和上传域名是否使用 HTTPS、白名单和平台合法域名；小程序敏感
  API 的权限声明、用户授权交互和隐私说明必须与实际调用一致。
- 检查依赖版本、安装脚本、构建脚本和动态加载边界；不因依赖扫描没有告警就宣称业务输入
  已安全。

### 5. 样式、交互、可访问性与跨端

- 按项目约定检查 CSS Modules、样式文件位置、命名、全局变量、页面安全区、TabBar 遮挡、
  固定定位和滚动容器；不得把“视觉相似”当作布局正确。
- 检查点击区域、禁用态、聚焦/键盘替代操作（适用时）、颜色对比、文字截断、动态字号、
  图片尺寸、空状态和错误提示是否让用户能完成任务。
- 检查 H5 与小程序的事件、路由、存储、权限、文件上传、系统 API、CSS 单位和安全策略
  差异；不把单一平台截图当作跨端验证。
- 检查本地图片、SVG、远程图片和字体的命名、尺寸、协议、懒加载、占位和失败回退；避免
  未限制的 Base64、大图或用户可控 SVG。

### 6. 性能与可维护性

- 检查长列表分页或虚拟化、列表项稳定 key、图片懒加载、重复请求、无效响应式依赖、过大
  组件和不必要的全局刷新。
- 检查首屏包体、按需引入、重复依赖、构建产物异常增长和开发 Mock/调试代码是否泄漏到生产。
- 只报告有代码路径、构建分析或运行证据支持的性能问题；把“可能慢”标为风险并说明需要
  的测量方式。

## 测试与验证

1. 先读取 `package.json` 的实际 scripts 和锁文件，再选择仓库已有的包管理器；不得因为
   常见命令不存在而临时修改脚本、配置或生成新的锁文件。
2. 按本阶段范围运行可用的格式检查、Lint、类型检查、单元测试、组件测试和目标平台构建；
   Taro 至少核对目标端构建，其他平台没有执行就明确标为未验证。
3. 测试或手动验证至少覆盖：核心成功路径、校验失败、权限/鉴权失败、空数据、网络错误
   与重试、重复提交、快速切换筛选/返回、过期请求、路由参数和平台差异。
4. 检查已有测试是否验证业务结果和 UI 状态，而不只是渲染成功；测试设计、测试文件存在、
   测试命令返回成功和真实运行证据分别记录，不能互相替代。
5. 构建输出只能证明对应目标编译成功；不能据此证明真机权限、网络域名、视觉还原、后端
   联调或发布配置正确。需要时记录真机/模拟器/浏览器验证缺口。
6. 使用 `git diff --check`、构建日志、测试输出和必要的运行截图作为证据；不输出环境变量
   密钥、Token、个人信息或完整敏感响应体。

## 问题分级与证据

按影响而非修改行数分级：

- **P0**：可利用的高危安全问题、数据泄露、生产不可用或大范围数据/状态破坏。
- **P1**：核心流程不可用、鉴权/权限绕过、关键接口契约错误、跨端构建失败或严重状态错乱。
- **P2**：可稳定复现的功能缺陷、重要平台差异、错误/空状态缺失、明显性能或隐私风险。
- **P3**：可维护性、可访问性、样式一致性、调试残留或低影响优化项。

每条问题必须包含：

1. `P0-P3`、标题和置信度；
2. 文件绝对或仓库相对路径与具体行号；
3. 触发条件或最小复现步骤；
4. 实际影响和违反的项目规则/设计约束；
5. 推荐修复方向及需要补充的测试或验证；
6. 如果只是推断，写明尚缺的运行或环境证据。

没有证据支持的偏好不要写成缺陷。发现同一根因影响多个页面时合并为一个根因，并列出受
影响入口；修复建议不得扩大到未经用户授权的业务重构。

## 审计交付

按以下顺序输出：

1. 审计范围、基线、目标平台、工作区初始状态和未纳入范围；
2. 结论摘要：阻断项、主要风险、已验证通过项和验证缺口；
3. 按 P0 到 P3 排序的问题清单，逐条提供证据和修复建议；
4. 设计覆盖、代码覆盖、测试覆盖、跨端覆盖和安全覆盖的边界；
5. 实际执行的命令及结果，未执行或失败的命令及具体原因；
6. 建议的修复顺序和复审入口，不创建 commit，不把未执行内容写成通过。

如果用户随后要求修复：先确认修复范围，保留初始工作区差异；只修改明确问题涉及的文件，
完成后重新运行适用验证、复核 `git diff --check` 和审计清单，并单独报告新发现的问题。不要
自动暂存、提交或上传。
